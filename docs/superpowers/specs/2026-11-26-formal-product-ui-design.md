# Titan 正式产品 UI V1 设计

## 文档状态

- 状态：已确认，进入实现计划
- 日期：2026-11-26
- 目标用户：项目负责人 / Product Owner
- 产品形态：桌面优先的 Web 应用，兼容平板和小屏浏览器
- 产品定位：帮助项目负责人做出决策、推动项目阶段、审阅交付物

## 1. 背景与问题

Titan 当前已有一套本机验收控制台，能够验证 Project、Task、Session、Run、Artifact、Daemon、凭证和事件链路。它的导航和文案围绕开发验收设计，适合工程人员检查系统行为，不适合作为项目负责人日常使用的产品入口。

正式产品需要把执行基础设施隐藏在项目语境之后。项目负责人首先需要知道项目是否健康、哪些事项需要本人决定、项目经理建议如何处理，以及选择会对目标和交付造成什么影响。Run、Daemon、Tool 和原始事件只能在用户主动深入执行详情时出现。

## 2. 产品目标

### 2.1 V1 目标

1. 用户打开产品后，能立即看到需要自己处理的决策事项。
2. 用户能理解每个决策的背景、项目经理建议、影响和下一步。
3. 用户能从决策进入项目空间，查看目标、里程碑、风险、阶段、Agent 工作和交付物。
4. 用户能在项目空间中继续询问项目经理、查看进度、启动新的工作目标。
5. 用户能审阅正式交付物，并沿来源、版本和评审状态追溯到项目阶段。
6. 用户能在不理解底层 Runtime 的情况下完成“目标 → 决策 → 执行 → 交付”的核心路径。

### 2.2 非目标

- V1 不提供多人实时协作、Presence、团队 Inbox 和评论协作。
- V1 不把 API Key、Daemon、Tool 调用和模型参数作为主导航内容。
- V1 不重新实现 Agent Runtime、Temporal、Session 或 Artifact 后端。
- V1 不把当前验收 UI 直接改名后作为正式产品交付。
- V1 不承诺公开 SaaS、多租户计费或生产级云调度。

## 3. 核心信息架构

### 3.1 全局导航

左侧主导航包含：

1. **我的决策**：默认入口，展示待批准、待选择、待确认和待接管事项。
2. **项目**：项目列表及项目空间入口。
3. **交付物**：跨项目查看待评审、已批准和已交付结果。
4. **活动**：项目经理、Agent、Run 和系统产生的关键项目活动。

次级设置入口包含工作区、成员与权限、环境设置和账户菜单。开发执行细节位于项目空间的执行详情中，不进入全局主导航。

### 3.2 默认首页：我的决策

首页由三部分组成：

- **今日判断**：用一句话总结待处理数量、最高影响事项和项目整体健康度。
- **决策队列**：按影响和紧迫程度排序的决策卡片。
- **项目脉搏**：最近项目的里程碑、趋势、风险、最近交付和项目经理摘要。

首页唯一主操作是“处理此事项”。询问项目经理、查看项目进度和启动新的工作目标作为次级入口。

### 3.3 项目空间

项目空间采用混合视图：

- 顶部显示项目名称、目标、健康度、当前里程碑、风险和待决策数量。
- 中部显示项目叙事，按目标、关键决策、阶段推进和交付物组织。
- 下部显示项目经理对话、当前 Agent 工作和最近交付物。

项目空间的主操作仍然是处理待决策事项。其他操作必须明确标记为次级操作。

### 3.4 决策详情

决策详情必须回答：

1. 发生了什么？
2. 为什么现在需要决定？
3. 项目经理建议什么？
4. 可选方案及其影响是什么？
5. 选择后会推进哪个项目阶段或工作项？

底部提供一个主要决策按钮，按钮文案根据决策类型变化，例如“批准方案”“选择继续本机执行”“要求重新设计”“接管此问题”。拒绝、取消或返回属于次级操作，并且必须保留明确的后果说明。

## 4. 视觉与交互方向

### 4.1 设计概念

采用 **Decision Desk / 决策工作台**：克制、可信、偏编辑型的项目管理界面。视觉重点放在结论、影响和下一步，而不是技术指标堆叠。

正式产品与验收控制台使用不同的视觉语言：

- 正式产品使用“项目、目标、判断、交付、风险”等产品语言。
- 不在首页出现 `LOCAL`、`PHASE`、`EXECUTION ENGINE` 等验收标签。
- 不使用开发控制台式的密集表格作为默认内容。
- 使用温和的纸张背景、深墨色文字、蓝绿色行动色和琥珀色风险色，避免紫色渐变和通用 SaaS 模板感。
- 标题使用具有编辑感的衬线字体，正文使用清晰的人文无衬线字体；代码、ID 和时间使用等宽字体。

### 4.2 交互规则

- 每个页面只有一个主操作。
- 决策卡片必须显示状态文本，不能只用颜色表达风险或优先级。
- 所有操作提供加载、成功、失败和可恢复路径。
- 需要确认的动作显示影响和回退方式。
- 支持键盘导航、可见焦点、语义标题、`aria-live` 状态播报和减少动画模式。
- 桌面宽度优先使用持久侧栏；小屏改用顶部导航和抽屉。
- 关键页面支持 URL 深链接，浏览器返回能保留列表筛选和滚动位置。

## 5. 组件边界

正式 UI 与现有验收 UI 分层：

- **产品壳层**：全局导航、工作区切换、用户菜单、通知和响应式布局。
- **决策域组件**：决策列表、决策卡、影响摘要、选项比较、批准动作。
- **项目域组件**：项目健康度、里程碑、项目叙事、项目经理摘要、项目活动。
- **交付域组件**：交付物列表、版本、来源、评审状态和正文预览。
- **执行详情组件**：Session、Run、Daemon、工具事件和恢复操作；复用现有 API 能力，但使用正式产品的详情视觉。
- **设置组件**：环境、凭证和权限设置；沿用现有安全边界，不在浏览器保存 Secret。

现有 `TaskWorkspace`、`RunWorkspace`、`RunEvents` 和 `ArtifactExplorer` 作为执行详情的能力来源，不能直接作为正式首页布局。

## 6. 数据与状态

V1 优先复用现有控制面事实：Project、Task、Artifact、Session、Run、Event 和本机状态。新增正式 UI 所需的产品视图模型应在前端组合层完成，避免为展示重复创建领域事实。

决策事项需要一个明确的适配边界：

- 已有审批状态和阶段推进可映射为“批准阶段”决策。
- 已有运行状态、暂停、恢复、取消和错误可映射为“执行选择”和“异常接管”决策。
- 已有 Artifact 评审状态可映射为“交付物评审”决策。
- 当后端尚未提供真正的决策队列时，UI 不生成演示数据；应显示空状态或明确的“当前能力尚未接入”状态。

## 7. 错误与空状态

- 无项目：引导创建第一个项目，并解释项目负责人能在这里完成什么。
- 无待决策：显示“当前没有需要你决定的事项”，同时展示项目脉搏和最近交付。
- 数据加载失败：显示具体原因、最后成功更新时间和重试入口。
- 决策版本冲突：提示内容已更新，要求重新读取并审阅，不覆盖他人的新版本。
- 执行失联：显示“等待恢复”或“需要接管”，不直接显示为失败。
- 权限不足：说明缺少的项目权限和可联系的责任角色。

## 8. 实现与验证策略

### 8.1 实现顺序

1. 建立独立正式产品壳层和路由边界。
2. 实现“我的决策”首页和决策卡片适配层。
3. 实现项目空间混合视图。
4. 实现决策详情和现有审批、阶段推进接口连接。
5. 将项目经理对话、交付物和执行详情接入次级入口。
6. 清理或隔离验收 UI 的产品入口，避免两套界面混淆。

### 8.2 验证门槛

- 前端类型检查、单元测试、生产构建通过。
- 使用真实控制面数据验证空状态、加载失败、版本冲突、运行失联和权限错误。
- 浏览器验证 1440px、1024px、768px 和 375px 宽度。
- 键盘完成决策列表浏览、打开详情、确认操作和返回列表。
- 检查 `prefers-reduced-motion`、焦点顺序和主要文本对比度。
- 验证正式产品首页不出现 Secret、Prompt、完整 Checkpoint、工具输出或未经授权的内部错误正文。

## 9. 完成定义

正式 UI V1 只有同时满足以下条件才算交付：

- 默认入口是“我的决策”，不是验收控制台。
- 项目负责人可以从首页理解事项并完成至少一种真实决策。
- 项目空间可以展示项目目标、健康度、里程碑、风险、Agent 摘要和交付物。
- 执行细节可深入查看，但不会主导默认信息架构。
- 所有后端操作使用现有认证、版本和幂等边界。
- 关键状态具有加载、成功、失败、冲突和恢复路径。
- 通过类型、测试、构建和浏览器验收，并记录证据。
